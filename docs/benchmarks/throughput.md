# Throughput & batching benchmarks

Evidence for Phase 5 ("honest batching"): the padded-batch equivalence gate and
the pre/post throughput tables that justify the shipped `max_batch_size` values.

## Method

* **Tooling.** `scripts/bench_throughput.py` (HTTP, `httpx` clients, warmup then
  `p50`/`p95`/mean latency and requests-per-second per concurrency level) and the
  `batching:1-vs-N` axis of `scripts/audio_regression.py`.
* **Host.** 3× RTX 5060 Ti 16 GiB; runs pinned with `CUDA_VISIBLE_DEVICES=1`
  (idle card). torch 2.9.1+cu130, Python 3.12.12, driver 610.88.
* **Build.** Working tree implementing Phase 5 on top of commit `7a34b06`
  (the harness records `HEAD`, which was still `7a34b06` at run time — the
  Phase 5 commit follows immediately after).
* **Engine.** A *reduced* config with only the models the four families need
  (`faster-whisper-tiny`, `ov2-synthesizer-en`, `ov2-tone-converter`,
  `ov2-tone-converter-encoder`, `chatterbox`, `chatterbox_embedding`), booted
  through the CLI (`python -m harmonyspeech.endpoints.openai.api_server
  --config-file-path … --port 2242`) so the measurement includes the serving
  layer, base64 audio I/O and WAV encoding.
* **Two sides.** `pre` = the pre-Phase-5 configuration of the *same build*:
  synthesizer/tone-converter/Chatterbox entries keep their old
  `max_batch_size: 10` and `batched_inference: false`, i.e. the historical
  per-item loops. `post` = the shipped Phase 5 values (synthesizer
  `max_batch_size: 8` + `batched_inference: true`, every loop-only handler `1`,
  Chatterbox `1`, Whisper `16`). Nothing else differs between the two configs —
  same build, same weights, same dtype, same GPU.
* **Load.** 16 requests per concurrency level (12 for the long-text runs),
  concurrency {1, 2, 4, 8}, 2 warmup requests per family, one text per family:
  "The quick brown fox jumps over the lazy dog near the river bank."
  (≈3.3 s of audio) unless marked *long text* (three sentences, ≈7 s of audio).
  Latency is measured per HTTP request; requests/s is wall-clock throughput of
  the whole level.
* **Reference audio.** `tests/audio_fixtures` (`repo_voice_a`, the repository's
  real-speech sample) for the clone/STT families.

Reproduce:

```bash
# terminal 1
CUDA_VISIBLE_DEVICES=1 python -m harmonyspeech.endpoints.openai.api_server \
    --config-file-path out/bench/config-post.yml --port 2242

# terminal 2
python scripts/bench_throughput.py --label post --requests 16 \
    --md-out docs/benchmarks/throughput.md
```

The reduced configs are regenerated by hand from `config.gpu.yml` (they are
benchmark fixtures, not shipped configs; the post file simply copies the
shipped values for those six entries, the pre file restores the old ones).

## Padded-batch equivalence gate

`scripts/audio_regression.py --axis batching:1-vs-4`, four different-length
texts through the same toolchain, **one** engine step on the batched side
against four separate one-request steps on the loop side. Both sides run with
`noise_scale = noise_scale_w = 0` (the models' sampling switches, exposed as
`generation_options.noise_scale` / `noise_scale_w` in Phase 5) and with TF32
disabled in the gate worker: that isolates padding/unpadding from sampling noise
and from TF32's batch-shape-dependent kernel choice. The comparison is
sample-wise on the rendered WAV.

| Family | Case (text length) | Verdict | duration Δ | max abs sample Δ | log-mel MSE | corr |
|---|---|---|---|---|---|---|
| melotts | short | PASS | 0.0 % | 1.59e-05 | 0.0 | 1.0000 |
| melotts | medium | PASS | 0.0 % | 1.59e-05 | 0.0 | 1.0000 |
| melotts | long | PASS | 0.0 % | 1.59e-05 | 0.0 | 1.0000 |
| melotts | shortest | PASS | 0.0 % | 1.58e-05 | 0.0 | 1.0000 |
| openvoice_v1 | short | PASS | 0.0 % | 0.0 (bit-identical WAV) | 0.0 | 1.0000 |
| openvoice_v1 | medium | PASS | 0.0 % | 0.0 (bit-identical WAV) | 0.0 | 1.0000 |
| openvoice_v1 | long | PASS | 0.0 % | 0.0 (bit-identical WAV) | 0.0 | 1.0000 |
| openvoice_v1 | shortest | PASS | 0.0 % | 0.0 (bit-identical WAV) | 0.0 | 1.0000 |

Verdict thresholds (`BATCHING_*` in the harness): duration Δ ≤ 0.1 %, max
|Δsample| ≤ 2e-3, log-mel MSE ≤ 1e-2, correlation ≥ 0.999. The measured
MeloTTS residual (1.6e-5) is below one 16-bit LSB; OpenVoice V1 reproduces the
solo run exactly after PCM16 encoding. The `1.59e-05` is expected float32
batched-kernel accumulation noise, not a measurement bug — see
[Numeric noise floor](audio-regression.md#numeric-noise-floor).

Unit-level proof of the same property (tiny randomly-initialised instances of
the vendored classes): `infer_batched` with `B=1` is **bit-identical** to
`infer`, and a sample inside a padded batch reproduces its solo run's predicted
frame count and post-attention prior exactly
(`tests/unit/modeling/test_batched_synthesis.py`).

## Throughput: pre vs post (short text)

MeloTTS synthesizer (`ov2-synthesizer-en`, `mode: single_speaker_tts`):

| Concurrency | pre req/s | post req/s | pre p50 (ms) | post p50 (ms) | pre p95 (ms) | post p95 (ms) |
|---|---|---|---|---|---|---|
| 1 | 8.32 | 8.29 | 119.5 | 120.0 | 125.1 | 125.5 |
| 2 | 8.61 | 8.64 | 231.8 | 230.4 | 234.4 | 237.8 |
| 4 | 10.66 | 11.47 | 376.1 | 344.1 | 389.5 | 368.9 |
| 8 | 12.62 | **14.43** | 629.2 | **543.9** | 657.0 | **568.9** |

`+14 %` throughput and `−13.5 %` p50 at concurrency 8, unchanged at c=1 (single
request always takes the per-item fast path). The gain is limited because a
single short sentence already keeps the GPU's kernels fed: at c=8 the server
forwarded 7–8 requests in **one** padded sub-batch per step (verified with
`HARMONYSPEECH_LOG_LEVEL=DEBUG`: `MeloTTS: 7 sentence(s) from 7 request(s)
forwarded in 1 padded sub-batch(es)`).

OpenVoice V2 full clone toolchain (Whisper VAD → tone-converter encoder →
MeloTTS → tone converter):

| Concurrency | pre req/s | post req/s | pre p50 (ms) | post p50 (ms) | pre p95 (ms) | post p95 (ms) |
|---|---|---|---|---|---|---|
| 1 | 1.86 | 1.84 | 537.0 | 532.3 | 559.0 | 559.4 |
| 2 | 1.94 | 1.91 | 1032.9 | 1044.6 | 1043.3 | 1063.2 |
| 4 | 2.05 | 1.87 | 1946.5 | 2100.6 | 2018.1 | 2505.4 |
| 8 | 2.13 | 1.90 | 3763.0 | 3861.7 | 3791.2 | 5966.7 |

No improvement — within run-to-run noise, slightly worse at c=8. The clone
pipeline is bound by its per-item hops (tone-converter encoder and tone
converter are `max_batch_size: 1` loops), so a faster synthesis step does not
move end-to-end throughput. This is why the tone-converter entries stay at 1
instead of pretending to batch.

Chatterbox TTS (the honesty check — autoregressive, `max_batch_size: 1`):

| Concurrency | pre req/s | post req/s | pre p50 (ms) | post p50 (ms) | pre p95 (ms) | post p95 (ms) |
|---|---|---|---|---|---|---|
| 1 | 0.61 | 0.60 | 1654.1 | 1643.0 | 1724.8 | 1763.0 |
| 2 | 0.61 | 0.61 | 3327.2 | 3268.6 | 3394.0 | 3408.7 |
| 4 | 0.56 | 0.59 | 7028.7 | 6724.7 | 7406.7 | 6956.5 |
| 8 | 0.61 | 0.60 | 12982.2 | 13066.6 | 13103.1 | 13350.0 |

Flat throughput with linearly growing latency in **both** configurations: with
the old `max_batch_size: 10` the "batching" was a lie (the handler looped), and
with the honest `1` the extra concurrency queues in the scheduler instead. Same
work, same rate, now truthfully described. Chatterbox capacity comes from
replicas, not from batching.

Whisper tiny STT (`BatchedInferencePipeline`, `max_batch_size: 16`):

| Concurrency | pre req/s | post req/s | pre p50 (ms) | post p50 (ms) | pre p95 (ms) | post p95 (ms) |
|---|---|---|---|---|---|---|
| 1 | 2.70 | 2.68 | 373.3 | 373.6 | 401.2 | 394.5 |
| 2 | 2.77 | 2.76 | 724.6 | 722.8 | 737.8 | 737.3 |
| 4 | 2.78 | 2.80 | 1433.1 | 1425.2 | 1461.9 | 1449.5 |
| 8 | 2.74 | 2.79 | 2905.2 | 2849.7 | 2947.0 | 2913.1 |

Unchanged, as expected: Whisper batches the *chunks inside one request*; across
requests the engine still runs one step at a time, so concurrency adds latency
at a constant rate.

## Length sensitivity (MeloTTS, long text ≈ 7 s)

| Concurrency | pre req/s | post req/s | pre p50 (ms) | post p50 (ms) |
|---|---|---|---|---|
| 1 | 4.18 | 4.28 | 235.6 | 231.6 |
| 8 | 5.80 | 5.93 | 1312.4 | 1303.6 |

For long texts the padded batch buys nothing measurable: a single utterance
already saturates the GPU, so batching amortises no launch overhead and adds no
parallelism. Capacity planning should therefore not assume batch scaling for
long-form synthesis; the batching win lives in short, sentence-sized requests.

## Notes & caveats

* p95 is computed over 16 samples per level (index-based percentile), so treat
  ±5 % as noise. The c=8 OpenVoice V2 post p95 (5967 ms) is a single outlier;
  its p50 matches pre.
* Both sides ran on the same idle GPU, sequentially, with the same weights
  cached locally; no other process used the card (checked with `nvidia-smi`).
* The `pre` side is the same binary with old configuration values, not an old
  commit. That is deliberate: it isolates the phase's *configuration* effect
  (which is what `max_batch_size` describes) from unrelated build differences.
  The code path difference is exactly `batched_inference: true` vs `false`.
* Logs, JSON reports and listening packs from these runs live under `out/`
  (untracked).
