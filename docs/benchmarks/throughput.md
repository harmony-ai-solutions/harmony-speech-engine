# Throughput & batching benchmarks

Evidence for Phase 5 ("honest batching"), Phase 7 (cross-request embedding
cache), Phase 8 (batching across every step) and Phase 10 (Whisper serving:
lanes, opt-in window batching, STT wire formats): the padded-batch equivalence
gate and the pre/post throughput tables that justify the shipped
`max_batch_size` values, plus the clone-flood and Whisper exhaustion scenario
matrices.

## Method

* **Tooling.** `scripts/bench_throughput.py` (HTTP, `httpx` clients, warmup then
  `p50`/`p95`/mean latency and requests-per-second per concurrency level) and the
  `batching:1-vs-N` axis of `scripts/audio_regression.py`.
* **Host.** 3× RTX 5060 Ti 16 GiB; runs pinned with `CUDA_VISIBLE_DEVICES=1`
  (idle card). torch 2.9.1+cu130, Python 3.12.12, driver 610.88.
* **Build.** Working tree implementing Phase 5 on top of commit `7a34b06`
  (the harness records `HEAD`, which was still `7a34b06` at run time — the
  Phase 5 commit follows immediately after).
* **Engine.** A *reduced* config with only the models the four families need
  (`faster-whisper-tiny`, `ov2-synthesizer-en`, `ov2-tone-converter`,
  `ov2-tone-converter-encoder`, `chatterbox`, `chatterbox_embedding`), booted
  through the CLI (`python -m harmonyspeech.endpoints.openai.api_server
  --config-file-path … --port 2242`) so the measurement includes the serving
  layer, base64 audio I/O and WAV encoding.
* **Two sides.** `pre` = the pre-Phase-5 configuration of the *same build*:
  synthesizer/tone-converter/Chatterbox entries keep their old
  `max_batch_size: 10` and `batched_inference: false`, i.e. the historical
  per-item loops. `post` = the shipped Phase 5 values (synthesizer
  `max_batch_size: 8` + `batched_inference: true`, every loop-only handler `1`,
  Chatterbox `1`, Whisper `16`). Nothing else differs between the two configs —
  same build, same weights, same dtype, same GPU.
* **Load.** 16 requests per concurrency level (12 for the long-text runs),
  concurrency {1, 2, 4, 8}, 2 warmup requests per family, one text per family:
  "The quick brown fox jumps over the lazy dog near the river bank."
  (≈3.3 s of audio) unless marked *long text* (three sentences, ≈7 s of audio).
  Latency is measured per HTTP request; requests/s is wall-clock throughput of
  the whole level.
* **Reference audio.** `tests/audio_fixtures` (`repo_voice_a`, the repository's
  real-speech sample) for the clone/STT families.

Reproduce:

```bash
# terminal 1
CUDA_VISIBLE_DEVICES=1 python -m harmonyspeech.endpoints.openai.api_server \
    --config-file-path out/bench/config-post.yml --port 2242

# terminal 2
python scripts/bench_throughput.py --label post --requests 16 \
    --md-out docs/benchmarks/throughput.md
```

The reduced configs are regenerated by hand from `config.gpu.yml` (they are
benchmark fixtures, not shipped configs; the post file simply copies the
shipped values for those six entries, the pre file restores the old ones).

## Padded-batch equivalence gate

`scripts/audio_regression.py --axis batching:1-vs-4`, four different-length
texts through the same toolchain, **one** engine step on the batched side
against four separate one-request steps on the loop side. Both sides run with
`noise_scale = noise_scale_w = 0` (the models' sampling switches, exposed as
`generation_options.noise_scale` / `noise_scale_w` in Phase 5) and with TF32
disabled in the gate worker: that isolates padding/unpadding from sampling noise
and from TF32's batch-shape-dependent kernel choice. The comparison is
sample-wise on the rendered WAV.

| Family | Case (text length) | Verdict | duration Δ | max abs sample Δ | log-mel MSE | corr |
|---|---|---|---|---|---|---|
| melotts | short | PASS | 0.0 % | 1.59e-05 | 0.0 | 1.0000 |
| melotts | medium | PASS | 0.0 % | 1.59e-05 | 0.0 | 1.0000 |
| melotts | long | PASS | 0.0 % | 1.59e-05 | 0.0 | 1.0000 |
| melotts | shortest | PASS | 0.0 % | 1.58e-05 | 0.0 | 1.0000 |
| openvoice_v1 | short | PASS | 0.0 % | 0.0 (bit-identical WAV) | 0.0 | 1.0000 |
| openvoice_v1 | medium | PASS | 0.0 % | 0.0 (bit-identical WAV) | 0.0 | 1.0000 |
| openvoice_v1 | long | PASS | 0.0 % | 0.0 (bit-identical WAV) | 0.0 | 1.0000 |
| openvoice_v1 | shortest | PASS | 0.0 % | 0.0 (bit-identical WAV) | 0.0 | 1.0000 |

Verdict thresholds (`BATCHING_*` in the harness): duration Δ ≤ 0.1 %, max
|Δsample| ≤ 2e-3, log-mel MSE ≤ 1e-2, correlation ≥ 0.999. The measured
MeloTTS residual (1.6e-5) is below one 16-bit LSB; OpenVoice V1 reproduces the
solo run exactly after PCM16 encoding. The `1.59e-05` is expected float32
batched-kernel accumulation noise, not a measurement bug — see
[Numeric noise floor](audio-regression.md#numeric-noise-floor).

Unit-level proof of the same property (tiny randomly-initialised instances of
the vendored classes): `infer_batched` with `B=1` is **bit-identical** to
`infer`, and a sample inside a padded batch reproduces its solo run's predicted
frame count and post-attention prior exactly
(`tests/unit/modeling/test_batched_synthesis.py`).

|---|---|---|---|---|---|---|
| 1 | 8.32 | 8.29 | 119.5 | 120.0 | 125.1 | 125.5 |
| 2 | 8.61 | 8.64 | 231.8 | 230.4 | 234.4 | 237.8 |

`+14 %` throughput and `−13.5 %` p50 at concurrency 8, unchanged at c=1 (single
request always takes the per-item fast path). The gain is limited because a
single short sentence already keeps the GPU's kernels fed: at c=8 the server
forwarded 7–8 requests in **one** padded sub-batch per step (verified with
`HARMONYSPEECH_LOG_LEVEL=DEBUG`: `MeloTTS: 7 sentence(s) from 7 request(s)
forwarded in 1 padded sub-batch(es)`).

OpenVoice V2 full clone toolchain (Whisper VAD → tone-converter encoder →

| 1 | 1.86 | 1.84 | 537.0 | 532.3 | 559.0 | 559.4 |
| 2 | 1.94 | 1.91 | 1032.9 | 1044.6 | 1043.3 | 1063.2 |

## Length sensitivity (MeloTTS, long text ≈ 7 s)

| Concurrency | pre req/s | post req/s | pre p50 (ms) | post p50 (ms) |
|---|---|---|---|---|
| 1 | 4.18 | 4.28 | 235.6 | 231.6 |
| 8 | 5.80 | 5.93 | 1312.4 | 1303.6 |

For long texts the padded batch buys nothing measurable: a single utterance
already saturates the GPU, so batching amortises no launch overhead and adds no
parallelism. Capacity planning should therefore not assume batch scaling for
long-form synthesis; the batching win lives in short, sentence-sized requests.

## Notes & caveats

* p95 is computed over 16 samples per level (index-based percentile), so treat
  ±5 % as noise. The c=8 OpenVoice V2 post p95 (5967 ms) is a single outlier;
  its p50 matches pre.
* Both sides ran on the same idle GPU, sequentially, with the same weights
  cached locally; no other process used the card (checked with `nvidia-smi`).
* The `pre` side is the same binary with old configuration values, not an old
  commit. That is deliberate: it isolates the phase's *configuration* effect
  (which is what `max_batch_size` describes) from unrelated build differences.
  The code path difference is exactly `batched_inference: true` vs `false`.
* Logs, JSON reports and listening packs from these runs live under `out/`
  (untracked).

## Phase 7 — Cross-request embedding cache (clone flood)

Evidence for Phase 7: the OpenVoice V2 clone toolchain starts with a speaker
embedding derived from the reference audio. With the cross-request cache enabled
([`docs/embedding-cache.md`](../embedding-cache.md)) repeated reference audio
should stop paying for that step; with distinct reference audio on every request
the cache cannot help and the run should be at parity with the cache disabled.

### Method

* **Tooling.** `scripts/bench_throughput.py --families openvoice_v2` with the new
  `--clone-reference` mode:
  * `same` — every concurrent request clones the **same** reference clip
    (`--reference repo_voice_a`). This is the worker-flood pattern: one voice,
    many requests.
  * `distinct` — each request gets a **different** deterministic variant of the
    base clip (sample-offset rotation + tiny gain change, encoded to WAV), so
    every request has a unique decoded `content_hash`: a guaranteed cache miss,
    i.e. the worst case. Variants keep the base clip's duration and sample rate,
    so VAD and the embedder see normal speech-length audio (no padding, no
    synthetic silence).
* **Two sides.** `cache-on` = the shipped default
  (`embedding_cache_enabled: true`, TTL 300 s, 1000 entries, 1 GiB); `cache-off`
  = the same build booted with `--no-embedding-cache`. Nothing else differs.
* **Load.** OpenVoice V2 clone pipeline (Whisper VAD → tone-converter encoder →
  MeloTTS → tone converter), concurrency {1, 4, 20}, 20 requests per level, 2
  warmup requests. One text: "The quick brown fox jumps over the lazy dog near
  the river bank."
* **Host.** Idle GPU (measured precedent: `CUDA_VISIBLE_DEVICES=1`, RTX 5060 Ti
  16 GiB), engine booted through the CLI so the measurement includes the serving
  layer and WAV decoding.
* **Scrape.** During each `cache-on` level, record
  `hse_embedding_cache_hit_ratio`, `_hits_total`, `_misses_total`,
  `_stores_total` and `_bytes` from `/metrics`; they are the proof that the
  latency delta comes from the cache and not from run-to-run noise.

Reproduce (per side, in two terminals):

```bash
# terminal 1 — cache on (default)
CUDA_VISIBLE_DEVICES=1 python -m harmonyspeech.endpoints.openai.api_server \
    --config-file-path out/bench/config-post.yml --port 2242

# terminal 2
python scripts/bench_throughput.py --families openvoice_v2 --concurrency 1,4,20 \
    --requests 20 --clone-reference same --label phase7-same-cache-on \
    --config-note "OpenVoice V2 clone, embedding cache on (default)" \
    --md-out docs/benchmarks/throughput.md

python scripts/bench_throughput.py --families openvoice_v2 --concurrency 1,4,20 \
    --requests 20 --clone-reference distinct --label phase7-distinct-cache-on \
    --config-note "OpenVoice V2 clone, embedding cache on (default)" \
    --md-out docs/benchmarks/throughput.md

# restart terminal 1 with --no-embedding-cache, then repeat both runs with
# --label phase7-same-cache-off / phase7-distinct-cache-off and the matching
# --config-note "… embedding cache off (--no-embedding-cache)".
```

### Expected shape (to be confirmed on the GPU run)

* `same` + cache on: the embedding step disappears from steady state, so p50 at
  every concurrency level should drop by the embed hop's cost; throughput rises
  because the tone-converter/synthesis hops that remain are the only per-request
  work.
* `distinct` + cache on ≈ `distinct`/`same` + cache off: a key derivation
  (sha256 over the decoded PCM) per request is microseconds, far below the run-to-run
  noise of the clone pipeline. Any material regression here is a bug, not a
  property of the design.
* `distinct` vs `same` at cache off: identical, which is the control that proves
  the variant generation itself adds no engine cost.
* Expect no change to the *tail* behaviour of the per-item tone-converter hops
  (`max_batch_size: 1`, see Phase 5): the cache removes a serial step, it does
  not add parallelism. (Phase 8 later batched those hops — see §Phase 8.)

### Result — the cache hits, but end-to-end latency does not move

The cache does exactly what it says: `same` + cache on reports a **0.98 hit
ratio** (61 hits / 1 miss after warmup), `distinct` + cache on a **~0** ratio,
and the disabled boots report zeros. Yet all four cells are the same within
noise (4.05–4.27 req/s at c=1, 6.38–6.53 at c=20; p50 233–242 ms at c=1).
**The embedding hop is not on the clone pipeline's critical path at these
loads**, so removing it buys nothing measurable. The win the phase promised is
real only in the *counter* sense (no repeated embedding work, lower GPU load),
not in wall time; the pipeline is bound by the per-request synthesis and
tone-conversion hops. Do not size capacity assuming a cache-latency win.

(The `same`/cache-on numbers are also the Phase 8 "cache on, same" row below —
same boot, same load.)

## Phase 8 — every step batches (flood)

Evidence for Phase 8: with the embedder (8-2), tone-converter (8-3), vocoder and
restorer (8-4) steps now running padded-batch forwards, the clone and
restoration pipelines should stop being capped by their serial hops. Phase 8's
win is **per-step batching**: within one engine step the models still execute
sequentially (see the honesty note at the end of this section); what changed is
that a step forwards one padded batch (or a few length-similar sub-batches)
instead of N single calls, so fewer kernel launches and host round-trips carry
the same request flood.

### Method

* **Tooling.** `scripts/bench_throughput.py`:
  * `--concurrency 1,4,20` (comma list; a single integer still works) plus one
    manual `--concurrency 200` run for the client-ceiling observation.
  * `--clone-reference {same,distinct}` (Phase 7-3) for the clone matrix, with
    `--embedding-cache {on,off}` now **verifying** the server's reported
    `/health` state and aborting on a mismatch — the cache toggle is a
    server-side flag, so the four cells need two engine boots.
  * New families: `openvoice_v1`, `harmonyspeech` (encoder → synthesizer →
    vocoder) and `voicefixer` (restore → vocode, `/v1/audio/convert`), plus
    `kitten` for the lanes curve.
  * `--engine-log <file>` parses the engine's DEBUG sub-batch lines for the
    level and reports the per-step composition (how many padded forwards one
    engine step needed, rows/requests covered) next to the end-to-end p50/p95
    and req/s. Run the server with `HARMONYSPEECH_LOG_LEVEL=DEBUG` and redirect
    its output to that file.
  * The HTTP client's connection pool is sized from the highest concurrency
    level instead of `httpx`'s default 100, so a 200-connection run measures the
    engine rather than the client's connection limit. `--http-max-connections`
    caps it deliberately when the client ceiling itself is the thing to record.
  * `--print-scenarios` prints the whole clone matrix (two boots + four runs).
* **Host.** Benchmark host: RTX 5060 Ti 16 GiB (idle; `CUDA_VISIBLE_DEVICES=1`),
  the same host as the Phase 5/7 runs. This repository's local dev GPU (GTX
  1050 Ti 4 GB) exists but is **not** the measurement host. torch/driver
  versions are recorded by the harness in the block header.
* **Build.** Working tree implementing Phase 8 on top of commit `dab303a`
  (`git rev-parse --short HEAD`; the harness records `HEAD`, and the Phase 8
  commit follows immediately after — same convention as the Phase 5 block).
* **Engine config.** The reduced benchmark config carries only the families
  below, with the Phase 8-6 capacity values:

  | Entry | `max_batch_size` | Mechanism |
  |---|---|---|
  | `ov2-synthesizer-en` (MeloTTS) | `8` | padded batch, token axis |
  | `ov2-tone-converter-encoder` / `ov1-tone-converter-encoder` | `8` | padded batch, mel-frame axis |

### Honesty note — steps stay sequential

**Within one engine step, models execute sequentially.** Phase 8's win is
per-step batched forwards — fewer kernel launches, better device utilisation,
fewer host round-trips — **not** cross-step parallelism. A single clone request
still walks VAD → embed → synth → tone-convert one hop after another, and a
model processes one step at a time. Overlapping different steps (or running
several engine replicas) is the separate worker-concurrency workstream; do not
read these numbers as pipeline parallelism.

## Phase 10 — Whisper serving (lanes + windows + STT wire formats)

Evidence for Phase 10: whisper requests no longer pile up behind one
sequentially executed model. Width (M CTranslate2 workers / lanes) and depth
(opt-in cross-request window batching) are both real, bounded by the device-level
memory governor (10-3), and the STT wire surface now includes subtitles and
translation (10-4). The **headline metric is p95 of short clips under mixed
load**, not just requests/second: the Phase 5-3 baseline was whisper tiny at
2.8 req/s flat from c=1 to c=8, with p50 growing linearly to ~2.9 s at c=8 and a
long recording able to block every short clip behind it.

**Status: measured on the benchmark host 2026-11-08.** RTX 5060 Ti, commit
`edac2ba`, torch 2.9.1+cu130. Whisper needed the cuDNN 8 shim (see the host note
under Method); with it the engine reports `runtime_device: cuda` and the
governance status `ok` (projected peak 1621.1 MiB). Two probe defects were found
and are recorded under [VRAM profiles](vram-profiles.md#phase-10-3--device-level-truth).

### Fairness proof — head-of-line blocking

One ≥10-min file arrives **first**, then 20 short clips (≈3 s each). The
sequential baseline is the Phase 5-3 whisper row (short clips queued behind the
long one); the two Phase 10 paths are the comparison.

| Path | Short p50 (ms) | Short p95 (ms) | Long finish (s) | Notes |
|---|---|---|---|---|
| sequential loop (M=1, no windows) | 1208.0 | 1314.2 | 3.03 | long file runs on the one worker; shorts interleave |
| lanes only (M=4, 3:1 short:long admission) | 1277.7 | 1383.5 | 3.13 | long lane cannot fill the step ahead of shorts |
| lanes + windows | 573.9 | 644.5 | 2.36 | short windows share the long file's batches |

All three paths completed 21/21 with zero loss and zero errors. Two honest
surprises:

* **Width alone does not buy fairness on this GPU.** M=1 and M=4 are the same
  within noise for shorts (1208 vs 1278 ms p50) and for the long file (3.03 vs
  3.13 s). CT2's `inter_threads` workers share one GPU, so lanes change *which*
  request gets the device, not how much of it there is — consistent with the
  M-sweep below.
* **The window batcher is the fairness win.** Shorts are ~2.2× faster
  (574 ms p50) and the 600 s file finishes in **2.36 s** vs 3.0–3.1 s, because
  its 20 windows ride the same formed batches as the shorts instead of decoding
  one at a time. This is the result that justifies the opt-in window path.

(One earlier M=4 run measured the long file at 18.9 s; a repeat on a warm boot
gave 3.13 s. The 18.9 s was a cold-start outlier — the first long request after
model load pays CT2 graph/allocator setup. The table uses the repeat.)

data. Lanes only (no window batching) to isolate width.

observe format/empty-response errors, so the host row for pairing errors is the
proxy; the local test is the true pairing proof.

### Memory-budget trip run

Boot with `whisper_vram_budget_bytes` **below demand** (e.g. 6 GiB on the 16 GiB
card) and run the same flood. The governor must shrink admitted windows, degrade
latency gracefully and never OOM/crash.

| Metric | Required | Measured |
|---|---|---|
| Configured budget (`/health` verified) | recorded | 6442450944 B (6 GiB) |
| `allowed_windows` under load | shrinks below the cap | **never shrinks — governor inert** |
| Max device used | holds at/below the budget | 1627979776 B (1.52 GiB) ≤ 6 GiB |
| Requests answered (loss) | 100 (loss **0**) | 100 (loss 0) |
| Completed / failed | no crash/OOM | 100 / 0 |
| p50 / p95 vs the unbudgeted run | graceful degradation | 8032.5 / 15675.3 vs 8044.8 / 15737.8 ms |

**The budget is not enforced at runtime, and a tighter budget proves it.** A
second boot with `whisper_vram_budget_bytes: 1073741824` (1 GiB) ran the same
flood: 100/100 answered, 0 loss, p50 unchanged, but **max device used 2097741824
B (1.95 GiB) — 95 % over the 1 GiB bound**. Root cause is a two-link chain, both
engine-side (frozen for this task):

1. The startup max-shape probe fails
   (`RuntimeError: No clip timestamps found. Set 'vad_filter' to True…`) on its
   all-zero probe audio, so `peak_activation_bytes` and `per_window_bytes`
   stay 0.
2. `allowed_windows()` returns `cap` unchanged when `per_window_bytes <= 0`
   ("do not throttle on a guess"), so admission never shrinks.

So the 6 GiB "trip" is a pass only because the workload (2.1 GiB) is below the
budget; the bound itself is advisory. The boot-time check (projected weights +
probe peaks) does run and would fail a genuinely over-budget catalogue.

**Local proof:** `tests/integration/test_whisper_exhaustion.py` mocks
`torch.cuda.mem_get_info` and drives the real `get_whisper_admission` →
`scheduler.schedule()` path: `allowed_windows` falls 6 → 2 → 1 (0 with the hard
stop), the scheduler admits exactly that many requests, and a 24-request flood
under the draining floor completes with zero loss.

|---|---|---|---|---|---|

| `faster-whisper-large-v3-turbo` | wanda4 (3.6 s) | **yes** | 0.0 | 0.0 | language `ja` = `ja`; probability 0.9907 vs 0.9888 (**Δ 0.0020**) |
| `faster-whisper-tiny` | 65 s tiled | **yes** | 0.0 | 0.0 | language `ja` = `ja`; probability 0.9507 vs 0.9585 (**Δ 0.0078**) |

**Gate verdict: substantive contract PASS; the harness's 1e-3 probability
tolerance failed and was widened.** Text, per-segment text, segment start/end
and language are bit-identical in all three cases; the only delta is
`language_probability`, 0.002–0.008 absolute (0.2–0.8 pp). This is the same
batch-shape kernel-selection effect documented as the float noise floor, not a
semantic difference: the batched path reuses the batch encoder output for
language detection. **Owner decision 2026-11-08 (Phase 11-0):** the tolerance is
now `1e-2` and `language_probability` is marked informational; the shipped
configs set `batched_inference: true`. The multi-window test passes outright.

Documented stochastic edge: the batched path pins `temperature=0` exactly like
`BatchedInferencePipeline.transcribe`; the only semantic difference is the
language-detection input on multi-window requests (first window vs the
concatenation of the first windows), stated in `docs/batching.md`. The harness
lives in `tests/e2e/stt/test_whisper_window_parity.py` (skipped unless
`HSE_WHISPER_PARITY_MODEL` points at a local CTranslate2 Whisper directory).

### Honesty notes

* **The window batcher is on in the shipped configs (dated decision
  2026-11-08, Phase 11-0).** It has a hermetic parity harness and safe
  fallbacks. The B=1 real-model parity gate ran (2026-11-08): text, segments,
  timings and language are identical on all three cases; only
  `language_probability` moves 0.2–0.8 pp, so the harness bounds it at `1e-2`
  and marks it informational. `batched_inference: true` is now the shipped value
  in both configs; `false` still forces the proven per-request path.
* **Width is now measured — and it does not help throughput.** `num_workers`
  only changes how many independent requests overlap on shared weights; the
  M-sweep above is flat within ±2 % at every width for both models. Keep the
  shipped 2/4 as a fairness/isolation knob, not a throughput knob.
* **Within one engine step, one model executes one step at a time.** The lanes
  overlap transcribes of the same model; they are not cross-model parallelism.
* `16` remains the admission/queue depth; the window cap
  (`whisper_window_batch_size`, default `8`) is a memory bound, and the
  per-request pipeline's intra-audio clip batch is `16`.

## Phase 9 — Chatterbox AR decode (AR-0 baseline)

AR-0 (9-1) is the baseline block for Phase 9. Before any architectural change
(the shared KV-cache pool in 9-2, the `ARBatchRunner` in 9-3), it removes two
pieces of pure-loss work from the T3 decode loop — a per-step
`output_attentions=True` request nobody reads on the English path and a
per-token `tqdm` hook — and pins the numbers the later 9-x tasks are measured
against. Behaviour is gated by a seeded bit-equality check on a tiny
randomly-initialised T3 (`tests/unit/modeling/test_chatterbox_ar0.py`): cleaned
vs upstream sample identical tokens for both `eager` and `sdpa` attention.

### Method

* **Change under test.** `harmonyspeech/modeling/models/chatterbox/t3_ar.py`
  (`ChatterboxT3AR(T3)`) replaces the upstream inference path for the English
  TTS role only: no attention tensors requested when no analyzer is attached,
  no progress bar (debug opt-in: `HSE_CHATTERBOX_T3_PROGRESS=1`). Everything
  else — prefill composition, CFG, sampler, EOS handling — is upstream's.
* **Before / after.** `before` = the same run on the parent commit (upstream
  `T3.inference`); `after` = this working tree. One boot each, same config.
* **Host.** Benchmark host: RTX 5060 Ti 16 GiB (idle; `CUDA_VISIBLE_DEVICES=1`),
  the same host as the Phase 5/7/8/10 runs. torch/driver versions are recorded
  by the harness in the block header.
* **Build.** Working tree implementing Phase 9-1 on top of commit `4081d97`.
* **Engine config.** `config.gpu.yml` — the Chatterbox TTS entry with
  `backbone_group: chatterbox-base` (the grouping the seam rides on) and
  `max_batch_size: 1` (unchanged until 9-6 measures the AR runner). Reference:
  `repo_voice_a` from `tests/audio_fixtures`.
* **Load.** `--families chatterbox --concurrency 1,4 --requests 20`, 2 warmups,
  one short text per request ("The quick brown fox jumps over the lazy dog near
  the river bank.").
* **Measurement status.** Measured on the benchmark host 2026-11-08 (commit
  `edac2ba`, RTX 5060 Ti, torch 2.9.1+cu130). "Before" is a worktree at
  `4081d97` (the parent commit, upstream `T3.inference`); "after" is the
  current tree with `batched_inference: false, max_batch_size: 1` so both use
  the per-request loop. Loads are `--mixed-lengths` on both sides (an earlier
  single-text run was not comparable and is not used).

### What to expect

* **Concurrency shape does not change.** The execution model is still `loop`

* **Where the loss actually is.** The shipped English config uses

  `output_attentions=True` on that path (it returns `attentions=None` with a

  On `eager` (which HSE forces for multilingual, whose analyzer needs the
  attention hooks) the flag really does materialise attention weights; the
  bit-equality gate covers both.
* **No behaviour change claimed beyond speed.** Token sequences are bit-identical
  to upstream under a pinned seed (unit gate), so the audio path is unchanged by
  construction.

### Phase 9-6 — three-way comparison (sequential loop vs AR-0 vs AR runner)

rows per request) and `chatterbox-turbo` (one row) are committed scope.

| Family | Mode | c=4 req/s | c=8 req/s | c=20 req/s | c=8 p50 (ms) | c=8 p95 (ms) |
|---|---|---|---|---|---|---|
| `chatterbox` | sequential loop | 1.68 | 1.72 | 1.74 | 4560.2 | 4781.9 |
| `chatterbox` | AR-0 (cleaned loop) | 1.62 | 1.69 | 1.72 | 4569.0 | 4953.8 |
| `chatterbox` | AR runner (4) | 2.09 | 2.13 | 2.25 | 3603.0 | 4242.7 |
| `chatterbox_turbo` | sequential loop | 4.61 | 4.58 | 4.62 | 1724.1 | 1785.8 |
| `chatterbox_turbo` | AR-0 (cleaned loop) | 4.43 | 4.41 | 4.43 | 1792.3 | 1844.8 |
| `chatterbox_turbo` | AR runner (4) | 5.29 | 5.59 | 5.44 | 1343.1 | 1580.1 |

Reading: both loop rows are flat with concurrency (one request per step), and
AR-0 ≈ sequential (AR-0 is a wash, see above). The AR runner is the only row
that rises: **+24–30 % for English** (2.09–2.25 vs 1.62–1.74) and **+15–21 % for
Turbo** (5.29–5.59 vs 4.41–4.62), with c=8 p50 down 21 % (English) and 25 %
(Turbo). It does **not** keep rising to c=20 because the 4-request admission
width (8 English slots / 4 Turbo slots) binds; p50 still grows with the queue.

**Critical caveat — the AR runner does not engage on CUDA in the shipped
build.** These "AR runner" rows were measured with a measurement-only wrapper
that fixes the pool's device (see *Open findings* #1/#2 under Method). In
the unmodified engine, `HarmonySpeechEngine` constructs `ARCachePool(...)`
without `device=`, so the pool is `torch.device("cuda")` (index `None`) while
`t3.device` is `cuda:0`; `ARBatchRunner.register()` compares them with `!=`
(False for `cuda` vs `cuda:0`) and **disables the runner for every CUDA model**,
silently falling back to the sequential loop. On this host the shipped
`config.gpu.yml` therefore produced `pool_bytes 0`, `grants 0`, and the
sequential numbers for every Chatterbox request. A second blocker applies to
voice cloning specifically: `chatterbox_embedding.max_batch_size: 1` serialises
the pipeline's embed step, so the TTS handler always sees one request and takes
its `len == 1` sequential fast path — even after the pool-device bug is fixed.
Raising it to 4 made the runner engage (grants 6, tokens/step 2.9) for
voice-cloning requests.

### Mixed-length rows

The AR flood rotates `CHATTERBOX_TEXTS` (`--mixed-lengths`) so short and long
rows leave a batch at different decode steps. The evidence is the
`hse_ar_decode_*` trace, not a padded sub-batch log: `tokens_per_step` is the
average active batch width, and it should fall as rows finish (a batch of 4
short + 1 long row narrows to 1 before the long row stops).

| Metric | Value |
|---|---|
| Max `hse_ar_decode_tokens_per_step` (batch width) | 3.96 (Turbo), 3.60 (English) |
| Min `tokens_per_step` before the last row finishes | not measurable from `/metrics` |
| Rows finishing before the longest row | not measurable from `/metrics` |

`hse_ar_decode_tokens_per_step` is a **cumulative average** (`tokens_total /
steps_total`), not an instantaneous width, so the "min before the last row
finishes" cell cannot be read from it; it would need a per-step trace. What the
average does show is that rows do not all finish together: with 4 requests × 2
English rows = 8 slots, the average active width is 3.6, i.e. rows leave the
batch before the longest row stops (a fully packed batch would average near 8).
This is the expected mixed-length shape, but it is weaker evidence than a
per-step trace — recorded as a metric-shape gap, not a pass.

### Host-run notes (2026-11-08) — how the AR-runner rows were obtained

* **Pool device (engine bug — fixed in 11-0).** The unmodified engine used to
  disable the runner on CUDA (`pool.device == cuda` vs `t3.device == cuda:0`).
  The AR-runner rows used `out/bench/serve_ar_pool_device.py`, a measurement
  wrapper that patches the pool's default device to
  `torch.device("cuda", current_device())`; the engine tree was untouched at
  measurement time. Every row is labelled "AR runner (4) … pool device patched".
  Phase 11-0 fixed device resolution in the engine, so the shipped build now
  registers the arena on the model's device; the fixture is no longer needed.
* **Voice-cloning admission (shipped in 11-0).** `chatterbox_embedding.max_batch_size`
  was raised from 1 to 4 for the voice-cloning cache/exhaustion runs; at 1 the
  pipeline's embed step serialises and the TTS handler never batches. Phase 11-0
  ships depth 4 with an honest `loop_admission` re-classification.
* **Seeded parity gate (9-6).** As written the gate was **red** for both
  families, and the cause was the runner, not the harness:
  `ARBatchRunner.step()` re-sampled a row that was already `finished` when the
  caller passed it again, so the gate's "step both until all finish" loop
  appended extra EOS/decoder tokens to the short row. Phase 11-0 guards finished
  rows in `step()`; the harness now passes **without loosening token equality**
  (probe: `out/ar_parity_probe.py`; English 21 tokens, Turbo 24 tokens, equal). The
  English gate also surfaces the downstream symptom: its stream contains
  several EOS tokens, and upstream `drop_invalid_tokens` then builds a
  multi-element index. Fix `step()` to skip finished rows (or fix the gate's
  loop) and the gate passes.
* **Distributional gate.** `scripts/audio_regression.py --axis batching:1-vs-4`
  was not run for the AR families: the AR runner is disabled in the shipped
  build (above), and with the wrapper the two sides are not a padded-batch pair
  (the runner is a token-level decode, not `infer_batched`). The seeded parity
  probe above is the available evidence.

## Phase 11-2 — S3Gen autocast

A **falsifiable experiment**, not a rollout: can S3Gen (the flow-matching mel
decoder + HiFT vocoder shared by chatterbox en / multilingual / VC, and turbo's
own meanflow variant) run under `torch.autocast` without audible degradation,
and does it buy throughput? Owner decision 2026-11-08: run it; a clean negative
is a valid outcome.

### What the gate is

`HSE_S3GEN_AUTOCAST` = `off` (default, byte-identical) | `bfloat16` | `float16`,
CUDA-only. Two wrap shapes:

* **Surgical** — inside our padded flow loop (`s3gen_batch._flow_batched`), the
  autocast context covers only the encoder and CFM decoder forwards; the ODE
  state updates, masks, unpadding and `mel2wav` stay float32 (the decoder's
  output is cast back to the flow dtype). This is the path every batched vocode
  and every seeded single-row vocode takes.
* **Blanket** — a loaded `S3Gen`'s `inference` method is decorated once at load
  (the same instance-level seam the loader already uses for dtype), so every
  solo path — the sequential English/Turbo loops, multilingual, VC's
  `generate`, the AR runner's per-row fallback — runs the whole upstream call
  under autocast. Wrapping `inference` (not `generate`) keeps the AR backbones
  out of scope: T3 is float32 on both sides, so the seeded token stream cannot
  diverge.

Correctness gate: `scripts/audio_regression.py --axis dtype:fp32-vs-autocast`.
Both sides keep `dtype: float32` (identical T3) and a fixed request seed; only
the env gate differs. The axis asserts the harness's **audibility** bounds —
log-mel MSE < 1.0 dB², correlation > 0.98, RMS Δ < 5 %, duration Δ < 0.1 % —
which are the deterministic-family bounds the repo already treats as
"inaudible for the same model, different arithmetic". They are calibrated by
Phase 4: casting S3Gen's *weights* to fp16 measured **8.9–141.6 dB²** with
correlations 0.05–0.76 and was judged audible (`docs/models.md` §Precision), so
1.0 dB² sits 9× below the known audible class. A batching-order bound (1e-2)
would fail *both* precisions and is too strict for a precision axis.

> overhead) and of the WDDM Shared Memory paging cliff fixed in 12-9 — **not**
> model long-context limits. Every table below supersedes them.

### Method

* **Tooling.** `scripts/bench_throughput.py --scenario longform` (a fixed,
  seeded paragraph fixture per family, `split_text` ON/OFF, single request and
  floods at c={1,4,8}, with melo/openvoice_v2 also at c=2) and the new
  `scripts/audio_regression.py` axes
  `longform:off-vs-on` (short-text byte identity) and
  `determinism:run1-vs-run2` (seeded chunked determinism).
* **Fixture.** One fixed **real-prose** paragraph shared by every family
  (owner-provided extract from *The Villainess Malfoy*, 2026-11-09): 807
  characters, 8 sentences, **4 chunks** at the server's unified 300-character
  default for **every** family (Phases 12-7/12-8 removed the earlier per-model
  Turbo 150 / Multilingual 75 budgets) — so a single long-form request can fill
  a 4-row AR admission batch by itself (H2). It is a module literal, not a
  generator — identical bytes on every host — and the pinned unit test carries
  its SHA-256 and the per-family chunk counts. The owner rejected the earlier
  word-index generator as unlistenable; the real sentences also exercise the
  em-dash narrative rule. The `audio_regression.py` axes keep their synthetic
  literals deliberately: those texts exist to exercise numeric identity/
  determinism gates and are never listened to.
* **Variants.** ON = `generation_options.split_text: true` with the budget left
  unset, so the server applies the unified **300-character** default for every
  family (Phase 12-9); OFF = `split_text: false`. Everything else (text, voice,
  mode, reference, seed, filters) is identical — the unit self-check asserts
  that. ON runs leave `crossfade_ms`/`sentence_pause_ms` unset unless a probe
  overrides them, so they measure the serving layer's Phase 12-5 defaults
  (**40 ms** equal-power crossfade / **120 ms** sentence pause; the pause is a
  two-sided fade in/out per Phase 12-6) and the stitcher's edge conditioning.
* **Fidelity gate (added 2026-11-09).** Throughput and latency alone cannot
  catch a model that speaks only part of the text — the gap that let Turbo's
  word-dropping ship unnoticed. `scripts/bench_throughput.py --scenario
  longform --fidelity` renders each family's fixture **once per variant**
  (default ON at the server's unified 300-character budget; add
  `--longform-split both` to score the OFF baseline), saves the WAVs under `out/bench/fidelity-12/`,
  transcribes them with faster-whisper **large-v3-turbo** (`--gpu` selects
  CUDA; otherwise CPU int8), `language="en"`, beam 5, and reports word edit
  distance plus words heard / reference. Normalisation is case- and
  punctuation-insensitive (apostrophes split), and the distance is the
  LCS-based `len(ref) + len(hyp) − 2 × LCS`, so a skipped word costs exactly
  one. **Transcription noise floor on this fixture: ~2–6 edit distance**
  ("Karina/Carina", "weaves/leaves"); values in that band are not model
  errors. A missing faster-whisper install fails with a clear message instead
  of a traceback.
* **Phase 12-5/12-9 note (2026-11-09).** The rows below were measured with the
  shipped join defaults — 40 ms equal-power crossfade and 120 ms two-sided
  sentence pause (Phase 12-6) plus stitcher edge conditioning — so they are
  directly comparable to a production boot. The earlier butt-splice (0/0) rows
  were retired with the pre-fix baseline.
* **Phase 12-6..12-9 note (2026-11-09).** The rows below postdate the audit
  fixes: two-sided pause fade, parenthetical-safe sentence splitting,
  Multilingual's restored `repetition_penalty = 2.0` + `AlignmentStreamAnalyzer`
  hook/EOS fix, `ARBatchRunner`'s raised KV-slot cap, deferred batched vocode,
  multi-token continuation steps, the unified 300-character budget, and the
  Phase 12-9 padded-batch memory budget (paging cliff — see below). `chunks/req`
  is 4 for every family, and these fidelity/throughput figures **are** the
  definitive post-fix record.
* **Load.** The post-fix sweep ran **4 requests per level** for the AR families
  and kitten at c={1,4,8}, and **8 requests per level** for melo and
  openvoice_v2 at c={1,2,4,8}; c=1 is the single-request latency. 2 warmups per
  variant. Four/five levels keep a long-form sweep bounded (each request is
  30–60 s of audio); pass `--longform-requests 20` to match the short-text flood
  convention exactly.
* **Host.** Idle benchmark host (RTX 5060 Ti 16 GiB, `CUDA_VISIBLE_DEVICES=1`).
  Headline rows use `INFO` logging; the per-step composition rows use a
  separate `DEBUG` boot with `--engine-log` (DEBUG depresses the clone pipeline
  ~3× — see the Method host note).
* **Observed vs expected chunks.** The HTTP response carries no chunk metadata,
  so chunks/request is computed client-side with the same splitter the serving
  layer uses, and the observed side is the engine DEBUG log's per-step
  composition (`parse_step_composition`). Recorded as a limitation, not hidden.

### Padded-batch memory budget — the WDDM Shared Memory paging cliff (Phase 12-9)

The pre-fix `split=off` melo / openvoice_v2 rolls were not CPU or model cost.
An unchunked paragraph is one very long row; `plan_batches` padded it against
its neighbours, so one c=8 step reserved 6.5–9.8 GiB in a single forward. On
this host that crossed the Windows WDDM driver's dedicated-VRAM limit and paged
into **Shared GPU Memory**, turning a ~2 s step into a 120–402 s stall — melo
c=8 p50 92 s, openvoice_v2 c=8 p50 402 s (watchdog trip). Phase 12-9 adds a
padded-area `default_token_budget` in
`harmonyspeech/task_handler/batching.py`:

* **`DEFAULT_PHONE_BATCH_BUDGET = 1024` phones** for the phone/token-axis
  synthesizers (MeloTTS, OpenVoice V1). Keeps `B=8` of ~128-phone chunks or
  `B=2` of ~500-phone sentences. Measured on GPU 2 (2026-11-09): 0.180 s/item
  at `B=2` (906 phones) vs 0.654 s/item at `B=1`; `B=8` (3,624 phones) was no
  faster while reserving 6,512 MiB. Peak reserved VRAM stays ≤ 1.8 GiB.
* **`DEFAULT_MEL_FRAME_BATCH_BUDGET = 7500` mel frames** for the mel-frame-axis
  tone converters (OpenVoice V2). Keeps `B=2` of a ~43 s paragraph (3,660
  frames each) or `B=8` of ~10.8 s chunks. Measured on GPU 2: 0.403 s/item at
  `B=2` (7,320 frames) vs 0.698 s/item at `B=1`; `B=8` (29,280 frames)
  reserved 9,796 MiB and stalled ~400 s. Peak reserved VRAM stays ≤ 2.6 GiB.
* **Per-contract AR KV-slot caps** (`ARBatchRunner` `preferred_cap_tokens`):
  **1152** for the Perceiver-resampled English/Multilingual contract (34 cond
  + ~118 text + 1,000 speech) and **1536** for `TurboContract` (376
  un-resampled cond + text + 1,000 speech). This replaces the single 1536-token
  default so the two 8-slot arenas stop over-reserving 720 MiB that the
  resident catalogue needs.

With the budgets in place, `split=off` melo reaches **1.35 req/s at c=8**
(p50 5,890 ms) and `split=off` openvoice_v2 **0.89 req/s at c=8** (p50
8,965 ms): no stall, no watchdog trip, and the c=1 single-shot latency is
unchanged (1,135 ms / 1,525 ms).

What the Phase 12-6..12-8 audit established — now confirmed on the host:

* **Base Chatterbox chunked at 300 is faithful** (edit distance 2) and keeps the
  unified 300-character budget: fewer chunks means better throughput.
* **Turbo's 300-character losses were engine truncation, not a model limit.**
  The shared autoregressive KV-cache slot was capped at **768 tokens** while
  Turbo's un-resampled conditioning prompt alone can be **376 tokens**, so the
  speech budget clamped to `768 − prefill` and the chunk was cut mid-sentence.
  Solo sentences bypassed that path entirely (upstream's solo loop gets the full
  1000-token budget), which is why they were perfect. Phase 12-8 raised the slot
  capacity so a 300-character chunk gets its full generation budget; the
  150-character per-model workaround is gone. **Post-fix: 4 at 300 chars.**
* **Multilingual's 300-character losses were a premature EOS, not budget
  sensitivity.** The engine passed `repetition_penalty = 1.2` instead of
  upstream's **2.0** into `AlignmentStreamAnalyzer`'s repeat detector, and leaked
  three attention hooks per call (forcing slow eager attention). Phase 12-7
  restored the upstream penalty and fixed the hook/EOS path, which also enables
  fast attention plus batched decoding and batched vocoding. **Post-fix: 0
  unchunked and 4 chunked, full coverage; the 75-character workaround is gone.**
* **Melo and OpenVoice V2 were unaffected** (edit distance 0–2 in both modes).
* **Kitten is within/at the floor** (6–8, 138/138 words in both modes).
* **The earlier "+35 % audio length when chunked" for Turbo was an artifact** of
  comparing against the word-dropping unchunked baseline: per-word pacing is
  equal (2.13 MB / 137 words vs 1.48 MB / 88 words); there is no pacing problem.

### Finding — the shipped config does not fit the recorded long-form envelope on a 16 GiB card

The OV2 cliff on the shipped config is **not a Phase 13/14 regression**: the
same tree reproduces the recorded 12-9 numbers on the 8-entry

`Config: out/bench/config-phase12.yml`). The difference is residency:

|---|---|---|---|
| 12-9 fixture (`config-phase12.yml`) | 8 | 10.7 GiB | **5.6 GiB** |
| shipped `config.gpu.yml` (whisper CPU-fallback) | 28 | — | ~2.5–3.5 GiB |

The Phase 12-9 padded-area budgets cap a TC batch at 7500 mel frames
(~2.6 GiB peak reserved), which fits the fixture's 5.6 GiB headroom but not
the shipped catalogue's: long-row TC batches page into WDDM Shared Memory and
the 12-9 cliff returns (on/c=1 1478→7150 ms; off/c=8 →88 s — the exact
pre-12-9 signature the fixture header itself documents). Two shipped-config
gaps for the owner to weigh (recorded here, not fixed in this phase):
1. The 12-9 matrix is a **fixture-config result**; the reproduce block's
   `--config-file-path config.gpu.yml` line does not match what was booted.
2. A 16 GiB card cannot host all 28 models + the 2.75 GiB AR pool and still
   serve long-form OV clone floods; options are a slimmer default catalogue,
   lazy/secondary-device residency for the seldom-used synthesizers, or
   documenting the envelope (the shipped `request_timeout_s` default of
   120 s also clips unchunked c≥8 floods — the fixture sets 600 s for exactly
   this reason).
